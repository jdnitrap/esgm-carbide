As of 2026-09-13, `esgr/` (a sparse graph-based reasoning system at `/home/admin/Downloads/esgr/` — memory lives only on edges, kWTA-sparse nodes, pure local Hebbian learning, no backprop) gained real architectural additions in one long session, all user-directed:

**1. Reward-modulated (three-factor) Hebbian learning.** `ESGRGraph.modulation` (per-node, neutral=1.0), nudged by new `graph.reward()`/`graph.punish()`, called from `FactGate.confirm()`/`reject()`. `tick()`'s weight update: `eta*mod*x_u*x_v - lambda*w`. Tuned against real data (see [[feedback-tune-against-real-data]]): amount=0.3, modulation_decay=0.97 (half-life ~23 ticks) — 0.5 nearly pinned modulation at its ceiling under real stacked confirmations from the live graph.

**2. Dynamic node growth — the 300-node ceiling is no longer architecturally fixed.** `ESGRGraph.grow(n)` appends fresh nodes + random-topology edges at runtime, append-only, verified 0 frozen edges disturbed. Wired into `shell.py`'s `tile` command. Also fixed same session: `tile`'s free-node search didn't exclude the role-hub range (275-280) — would have silently overwritten NOUN/VERB/etc.

**3. `add_learnable_edge()`** — closes the other half of the original "fixed wires plus grow/prune" gap: can now create a genuinely new, ORDINARY (non-frozen) edge at runtime, not just frozen ones via `add_fixed_edge`.

**4. `FactGate(auto_confirm=True)`** with a separate, stricter `auto_confirm_min_tau=0.95` floor (above the normal 0.8 propose threshold) — an edge can confirm itself with no human call, but a borderline candidate still gets left for a human. Off by default. Deliberately overrides "not a fact until confirm()" at explicit user request.

**5. Important identity clarification from the user, supersedes a too-literal reading of the README:** the load-bearing design constraint is **"not a transformer, not an SSM"** — not a blanket ban on gradient descent anywhere in the system. A small, separate, bolt-on trained component (that never backprops into the graph's own edges) does NOT violate the project's identity, as long as the graph itself stays fully edge-inspectable/confirm-reject-able. This matters a lot for any future "should we add a trained head" discussion — don't over-restrict based on the README's literal "no gradient descent anywhere in the system" line.

**6. `supervise.py` — built, tested honestly, found NOT worth keeping as-is.** A local, single-hop, ground-truth-corrected learning rule (push toward the real next word from real corpus text even when it isn't currently active, suppress the wrong top-scoring competitor) — explicitly NOT backprop, single edge, fully traceable. Measured against real corpus data with a proper held-out split and, critically, against a trivial "per-context majority vote" baseline:
- Strict adjacency: graph=51.8%(held-out, vs a naive 0% no-training baseline) but only **54.8%** for a two-line counting script on the identical split — the graph mechanism did NOT beat trivial counting.
- Only **6 of 31 words** ever appear as a "context" word in real adjacent vocab pairs (17,033 pairs) — real, severe data sparsity, not a bug.
- Widening the adjacency gap tolerance (tried 1/3/8/20) pulled in more context words (6→8→11) but **plateaued at 11/31** and made the graph-vs-baseline gap WORSE (26.6% vs 36.5% baseline at gap=20) — looser pairing just added noise. Widening gap does not fix sparsity.
- **Conclusion, and the reason for pivot #7 below: most of this 31-word vocabulary essentially never co-occurs adjacently with other vocabulary words in this real corpus, at any gap tolerance.** This is a real property of the corpus/vocabulary pairing, not a flaw in the learning rule. `supervise.py` is left in the repo (working, tested, honestly documented) but not currently used by anything downstream — a future larger/richer corpus or vocabulary might make it worth revisiting.

**7. Pivot to more hand-coded mechanics — `grammar_extra.py`.** Given #6's finding, user explicitly chose to hard-code more English structure rather than chase learned correction further ("there is more language mechanics in the English system"). Added 4 new dimensions beyond the original 6 syntactic ROLEs, same frozen-edge pattern as `word_structure.py`, grounded in the REAL 31-word vocabulary (not invented): **TENSE** (PAST: sat/ran, PRESENT: is/likes/eats), **NUMBER** (SINGULAR: I/he/she/it, PLURAL: we/they — "you" deliberately left out, real English ambiguity), **ANIMACY** (ANIMATE: cat/dog/bird/fish/man, INANIMATE: mat/house), **DISCOURSE** (AFFIRM: yes, NEGATE: no, NEGATOR: not — finally gives the three words `word_structure.py`'s ROLE_MAP always left role-less a real grammatical home, in the linguistically correct separate dimension rather than forcing them into ROLE). Uses `graph.grow()` for hub nodes (9 new: 300→309) instead of hunting for free ids. Verified: all real word→value assignments correct, 0 existing frozen edges disturbed, full test suite still passes.

All changes verified against the full test suite (`test_graph_sanity.py`, `test_fact_gate.py`, `test_sequence.py`, `test_integration_stress.py` against the real `graph.json`) — all pass throughout.

**Natural next step, not yet done:** none of `sequence.py`/`decode.py` consume TENSE/NUMBER/ANIMACY/DISCOURSE yet — they're wired and queryable (`get_value`/`words_with_value` in `grammar_extra.py`, mirroring `word_structure.py`'s `get_role`/`words_with_role`) but not yet used to constrain generation (e.g. tense agreement across a sentence). That's the obvious next extension if picked back up.

**8. Real vocabulary expansion, persisted: 31 → 130 words (`expand_vocab.py`).** Mined the actual top 100 most-common real words in the 5MB corpus not already tiled (of, and, to, are, human, world, consciousness, ...), tiled via the exact same free-slot-then-`grow()` logic as `shell.py`'s `tile` command, extended `word_structure.ROLE_MAP` with confident-only role assignments (left genuinely ambiguous words like "and"/"that"/"but"/"than"/"present" without a role, same "real none" convention). Real corpus coverage: 6/31 (19%) words ever appeared as a training "context" before → 99/130 (76%) after. `graph.json` grew 300→399 nodes, 2667→4244 edges.

**Two real bugs found and fixed while persisting this (both worth knowing about for any future graph-size change):**
- **Name collision:** `"space"` is both a real English word AND the reserved tiles.json key for the space *character* (byte 32) — mining code excluded `space`/`A`/`newline` from the "already have it" check by name, meaning the real word "space" got mined as new and silently overwrote the character tile. Fixed the root cause in `expand_vocab.py` (exclusion set is now ALL existing keys, not a curated subset) and restored the correct value.
- **Silent out-of-bounds edges:** `add_fixed_edge()` never validated `src`/`dst < graph.n` — a smaller graph (e.g. a fresh `n_nodes=300` test/demo graph) given the real, now-bigger `tiles.json` would silently create an edge to a node it doesn't have, only crashing later, confusingly, inside `tick()`. Fixed: `add_fixed_edge()` now raises immediately with a clear message; `word_structure.wire_word_structure()` now skips (doesn't crash on) any tiled word whose node id doesn't fit the graph it's given.

**9. Real, latent min/max bug found and fixed in `_enforce_sparsity`'s temperature path (`graph.py`).** `pool_size = min(x.shape[0], max(k*3, positive_count))` — the function's own docstring says the pool should be "a generous multiple of k, OR every positive value if fewer", i.e. `min(k*3, positive_count)`. The code had `max`, the opposite. This bug is OLD, not introduced this session — it just never mattered on the original sparse 300-node graph, where `positive_count` rarely exceeded `k*3` so `max`/`min` agreed by coincidence. Growing the graph (item 8) exposed it for real: on the bigger, denser real graph, `positive_count` routinely hit 326/399, ballooning the softmax sampling pool to 326 candidates and destroying temperature-based generation (measured: 1/6 grammar-role matches, consistently, across 10/10 seeds). Fixed to `min`; reverified 10/10 seeds back to 6/6. **Lesson: this class of bug (an operator that "looks right" only because of the data scale it was written and tested against) is exactly the kind of thing that surfaces when you change scale — worth extra scrutiny on any code with a `max()`/`min()` involving a data-dependent count whenever n or vocabulary size changes again.**

All of the above reverified against the full test suite after every fix — all 4 test files pass.
